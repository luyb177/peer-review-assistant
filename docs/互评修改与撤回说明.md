# 互评记录修改与撤回

更新日期：2026-10-16。

## 1. 功能与权限

| 当前条件 | 查看 | 修改本人评分 | 撤回本人评分 |
|---|---|---|---|
| 学生本人、已完成、作业互评中、未截止 | 是 | 是，显式进入编辑 | 是，确认后删除评分 |
| 学生本人、待互评 | 是 | 不适用，应新提交 | 不适用，没有评分可撤回 |
| 其他学生的任务 | 拒绝 | 拒绝 | 拒绝 |
| 教师查看所属课程任务 | 是 | 拒绝代改 | 拒绝代撤回 |
| 作业已结束或互评已截止 | 是（按原权限） | 拒绝 | 拒绝 |

有效时间为互评开始（含）至截止（不含）。服务层再次检查，不以按钮显示状态作为权限保证。

## 2. 学生操作

1. 在「我的互评任务」选择记录，点击「查看 / 填写互评」。
2. 已完成记录先以查看模式展示分数和人工评语。
3. 点击「修改评分」，编辑分项及人工评语。可点击「计算当前分数」预览，预览不会保存。
4. 点击「保存修改」并确认，系统重新校验、计算、保存并刷新任务和统计。
5. 点击「撤回互评」并确认，会删除本次人工分数、评语和评分明细，任务恢复为待互评。
6. 撤回后重新打开任务，人工输入框为空；须重新独立填写并提交。

撤回不是取消任务分配，不会减少该提交的分配人数，也不删除 AI 参考意见。AI 仍不能自动代填人工评分。

## 3. 数据一致性

- `updateReview`：锁作业行→重读并检查任务和旧版本→校验分项和评语→更新 reviews（version+1）→替换 review_scores→写审计→提交。
- `withdrawReview`：锁作业行→重读并检查任务和旧版本→删除 review_scores→删除 reviews→任务改为 PENDING→写审计→提交。
- 任一步失败均回滚，不能出现“分数已改但明细没改”“记录已删但任务仍完成”或“保存成功但审计失败”的半成品状态。
- 汇总统计实时聚合有效 reviews，不缓存旧总分。修改立即改变均值/极值；撤回使已评人数减少，最后一份撤回后统计为空，不是 0 分。
- 事务锁顺序与原有提交、分配、关闭流程一致，复用独立连接和 READ_COMMITTED。

## 4. 旧窗口与并发

评分查询返回 `reviewId` 与 `version`：

- 首次提交：新 reviewId，version=1。
- 修改：同一 reviewId，version 递增。
- 撤回重交：新的 reviewId，version 从 1 开始。

修改和撤回必须携带打开窗口时的两项标识。另一个窗口已经保存、撤回或重交后，旧窗口会提示关闭并刷新，而不是覆盖当前成绩。只比较 version 不够：撤回重交后又是版本 1，还需要 reviewId 区分记录身份。

审计动作：`UPDATE_REVIEW`、`WITHDRAW_REVIEW`，包含任务、记录、版本和总分摘要。不把密码、Key 或评语正文放入日志。这是操作审计，不是可恢复所有历史正文的完整版本档案。

## 5. 现有数据库升级

新数据库的 `src/main/resources/schema.sql` 已包含：

```sql
version BIGINT NOT NULL DEFAULT 1
```

旧库由管理员在正确的专用库执行一次 [sql/01-review-version.sql](../sql/01-review-version.sql)。执行前查询 information_schema.columns；已存在 version 时不重复运行 ALTER。普通运行账号不需要也不应增加 ALTER 权限。

当前 lty-server-1 专用库已升级。升级前后 10 张表行数相同：4 个用户、1 门课程、1 份作业、3 项规则、3 份提交、6 条任务、6 份评分、18 条评分明细、1 条 AI 意见、39 条日志。这是**升级瞬间的核对值**，不是后续验收结束的总量。

旧记录默认版本 1，没有重建表、清空或改写已有分数。缺版本字段时，初始化检查和评分读取会给出管理员升级提示，不会提示用户清库重建。

## 7. 公网联调时的连接问题

本次公网握手在登录前中断。服务端检查确认 MySQL 健康、13306 监听正常、未耗尽连接；阻断项是 Docker 自定义 `TCM-DB-ACCESS` 链仍只允许旧出口 IP。

用户明确选择“取消 MySQL 白名单”后：

- 只移除该链针对 13306 的来源放行/拦截两条规则，Redis 16379 和 SSH 等其他规则不变。
- 同步 `/usr/local/sbin/tcm-database-access` 中对应两行，保留服务器端原脚本备份，防止重启恢复旧限制。
- 正式配置保持原公网地址；应用没有绑定 SSH 隧道。
- 临时备用隧道和临时账号已清理。
- 公网握手恢复，原配置 JDBC 连接成功约 0.62 秒。应用数据库账号仍受精确来源和 TLS 限制，只具有专用库读写权限。

因此不能把此次问题简单归结为 TUN 或“IP 无法访问”。ping、TCP 连接和数据库协议握手是不同层次，需要分别验证。
