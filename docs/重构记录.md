# 评分业务：从具体类依赖重构到策略模式

本记录对应实际编码过程，不是虚构的历史提交。当前尚未执行 Git 提交。

## 重构前

首轮实现中，`PeerReviewService` 直接创建具体评分计算器：

```java
private final ScoreCalculator scoring = new ScoreCalculator();

public PeerReviewService(Database db, Clock clock, Random random) {
    this.db = db;
    this.clock = clock;
    this.random = random;
}
```

`ReviewDialog` 还会单独创建 `ScoreCalculator` 计算预览分。这意味着未来更换业务评分算法时，界面和业务层可能使用不同公式。

在上述阶段，实际运行了评分、分配、业务集成和工具测试：**31 项，0 失败、0 错误、0 跳过**。这为之后保持现有行为提供了回归基线。

## 重构后

1. 提取 `ScoringPolicy`，声明规则校验和分数计算契约。
2. `ScoreCalculator` 实现该接口，保留原有归一化加权公式。
3. `PeerReviewService` 通过构造函数接收策略，默认仍使用 `ScoreCalculator`。
4. 新增业务方法 `previewScore`，界面不再自行选择或创建计算器。
5. 预览和落库评分统一委托同一个策略。

```java
private final ScoringPolicy scoring;

public PeerReviewService(Database db, Clock clock, Random random, ScoringPolicy scoring) {
    this.db = db;
    this.clock = clock;
    this.random = random;
    this.scoring = Objects.requireNonNull(scoring);
}
```

## 效果和验证

- 业务流程不依赖具体评分公式，满足依赖倒置和关注点分离。
- 使用显式构造注入，没有为了课程作业引入大型依赖注入框架。
- `ScoringPolicyTest` 注入带计数的真实算法包装策略，验证界面预览和持久化调用同一个策略，并保持 75.00 的计算结果。
- 原有评分与生命周期测试继续作为回归保护。
- 没有为了展示模式而提供无需求依据的额外评分算法；未来有真实需求时可增加策略实现。

## 不采用的示例

不把 JDBC `Connection` 做成全局单例。共享连接会混淆事务边界和线程状态；当前每个操作独立获取连接，由 try-with-resources 关闭。数据库服务对象可以复用，但数据库连接本身不共享。
